# Pattern: Petname Systems (GNS)

A **petname** is a human-chosen local name assigned by a user to a cryptographic identifier. Petnames are the mechanism GNS uses to provide memorable names without requiring a globally agreed-upon namespace. The design is derived from the Simple Distributed Security Infrastructure (SDSI) and its use of transitivity to extend petnames across trust paths.

---

## Zooko's triangle

Zooko's triangle states that a naming system cannot simultaneously achieve all three of:

1. **Global**: the same name resolves to the same entity for all users worldwide.
2. **Secure**: names are cryptographically bound to their targets; forgery is infeasible.
3. **Human-meaningful**: names are memorable and legible to humans.

DNS sacrifices security (relies on trusted registrars and CA infrastructure). Blockchain naming (ENS, Handshake) attempts to achieve all three but requires a trusted token-based auction to resolve naming conflicts. GNS explicitly sacrifices global uniqueness of human-readable names.

| System | Global | Secure | Human-meaningful |
|--------|--------|--------|-----------------|
| DNS | Yes | No (without DNSSEC/CAs) | Yes |
| ENS | Yes (for registered names) | Yes (on-chain) | Yes |
| Handshake | Yes (for TLDs) | Yes (PoW) | Yes |
| GNS petnames | **No** | Yes | Yes |
| GNS zTLDs | Yes | Yes | **No** (base32 key) |

GNS covers both corners via two distinct name forms:

- **Petnames**: human-readable, locally unique, not globally unique.
- **zTLDs**: globally unique, secure, not human-readable (base32-encoded public key).

## How petnames work in GNS

A petname is created when a user adds a PKEY or EDKEY record in their zone:

```bash
# Alice assigns the petname "bob" to Bob's zone key
gnunet-namestore -a -n bob --type PKEY -V $BOBKEY -e 1d -z alice_zone
```

Now Alice resolves `anything.bob.alice_zone` by following the delegation to Bob's zone. Bob's zone may in turn delegate to Carol's zone under the label `carol`, creating a chain.

The same zone key may be assigned different petnames by different users:

| User | Petname | Zone key |
|------|---------|---------|
| Alice | `bob` | `AQAB...` |
| Carol | `robert` | `AQAB...` |
| Dave | `grothoff` | `AQAB...` |

None of these names conflict because they are all local to the respective user's zone.

---

## SDSI transitivity

GNS uses SDSI's concept of linked local names to make petnames useful beyond a single user:

If Alice trusts Bob (`alice_zone → bob → Bob's zone`) and Bob has mapped `alice` to Alice's zone in his own zone, then any user who trusts Bob can reach Alice via `alice.bob.BOBKEY`. The name is human-readable within the context of the trust path, though the absolute address still terminates in a key (`BOBKEY`).

This transitivity means that zone graphs can grow organically through social trust relationships without any central coordination.

---

## Bootstrap problem

The core practical challenge: to begin using petnames, Alice must first learn Bob's zone public key through some out-of-band channel:

- Scan a QR code.
- Receive a business card generated by `gnunet-bcd`.
- Trust a FCFS registrar's zone (see below).
- Find a zTLD posted on a website (resolving via the raw base32 key, then assigning a petname).

This bootstrap requirement is a real usability barrier. The GNS approach does not provide an equivalent of DNS's ability to type "facebook.com" into any browser without any prior configuration.

---

## FCFS registrar as a shared petname layer

The `gnunet-namestore-fcfsd` service provides a first-come, first-served web UI where users register a label under the registrar's zone (currently `.pin.gns.alt`). The registrar publishes a PKEY record mapping the chosen label to the user's zone key.

A GNUnet user who adds the registrar's zone as a petname in their own zone can then resolve any FCFS-registered name:

```
$USERNAME.pin.gns.alt → user's zone
```

Properties of this model:

| Property | Value |
|----------|-------|
| Registration policy | First-come, first-served; no fee (demo Taler KUDOS for testing) |
| Expiry | Registrations do not expire |
| Anti-squatting | None beyond FCFS; no renewal cost; squatting is possible |
| Centralisation | Single registrar zone key; trusting it reintroduces a central discovery authority |
| Record integrity | Not compromised by registrar: registrar only maps label to zone key; zone owner controls their own records |

The FCFS model is a pragmatic convenience layer for discovery, not a governance mechanism. It demonstrates that shared human-readable namespaces can be built on top of GNS without modifying the core protocol.

---

## Name squatting analysis

| Squatting incentive | GNS situation |
|---------------------|--------------|
| Squatting a globally canonical label | **Not possible**: no global human-readable namespace |
| Squatting on a FCFS registrar | Possible; FCFS is first-come, no expiry, no cost; but only affects users who choose to use that registrar |
| Pre-registering common words | Only matters within a specific registrar's zone; other registrars can offer the same label |
| Cybersquatting for resale | No market: petnames are not transferable assets with monetary value outside a specific zone |

Conclusion: GNS eliminates the economically motivated squatting problem by design. The FCFS registrar introduces a limited, localised squatting surface, but it is structurally different from DNS/ENS squatting because users can choose any registrar or use zTLDs directly.

## Behaviours relevant to RFP requirements

| Behaviour | Implication |
|-----------|------------|
| Petnames are local, not global | A DHT-based naming system MUST document that human-readable names are not globally unique by default |
| zTLDs provide global uniqueness | A naming system SHOULD provide a mechanism to reference any zone by its cryptographic identity without human-readable names |
| FCFS registrar as optional discovery layer | A naming system MAY provide a shared discovery zone via a FCFS registrar model; this MUST be clearly identified as a trust delegation, not a protocol guarantee |
| Out-of-band bootstrap is unavoidable | System design MUST include UX affordances for distributing zone keys (QR codes, shareable zTLD strings, etc.) |
| No squatting incentive without global namespace | Removing the global human-readable namespace eliminates the primary economic driver for name squatting |
